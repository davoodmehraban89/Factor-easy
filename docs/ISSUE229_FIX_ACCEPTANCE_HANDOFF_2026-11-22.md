### Required atomic command contracts (implementation owner: Codex-main)

1. **Save/Create/Edit commercial source with generated draft**: one server transaction, scoped to Auth user + active organization/company/fiscal year. Validate source identity, fields, version, required accounts/dimensions, and approved immutable posting-profile snapshot. Generate/upsert **exactly one draft** journal with matching source/version and balanced journal lines, bidirectional link, provisional number and permanent attachment reservation per ADR216. No posted timestamp, posted actor or **final-number consumption** on Save. Retry with stable idempotency identity; concurrent Save gets deterministic winner/version error. Failed call rolls back **both** source and draft; never show false success.
2. **Finalize existing source-linked draft**: distinct explicit server RPC, requiring `accounting:approve` on actual membership/entitlement **for every** sale/purchase path, not merely `commerce:create` or any JS `requireWrite`. Validate source and voucher version under lock; check organization/company/owner linkage, fiscal locks, debit/credit, dimensions, source state, and number reservation. In **one transaction** change voucher and source to posted; allocate exactly one final number; audit the real approver. A legitimate accounting-only approver may need a scoped accounting read path to validate the source; do not silently require commerce CREATE to approve.
3. **Block legacy bypass**: once draft-first RPCs exist, no direct `finora_journal_autopost` entry may allow `commerce:create`-only JWT to finalize. Prefer explicit versioned deprecation/restriction of the public RPC over a client-only toggle. Audit all other paths that reach `post_core(p_auto=true)` (including reversal workflows) for intended independent permissions; avoid blanket changes that silently break other source types.
4. **Update/Delete**: only linked drafts can mutate with optimistic versions, atomic recomputation and audit. Source deletion and generated draft tombstone are one transaction. Direct generated-voucher delete is rejected. Posted and reversed source/voucher/lines stay immutable; corrections use approved reversal + new linked draft, never mass `posted`→`draft` rewrites. Keep permanent attachment numbers reserved after deletion and separate fiscal numbering.
5. **UI/report projections**: on successful Save, show *source draft + linked journal draft*, route explicit Finalize to authorized approver with clear denial for seller, and render draft/posted/reversed accurately in purchase/sale/report filters. Avoid duplicate stock or expense effects by counting a single business event once. Prevent edited drafts from being mistaken for posted because they have `journalVoucherId`.
